Context: read docs/skills/breakout-with-volume-strategy/ (SKILL.md and references/), docs/breakout.config.yaml (seed parameters) and docs/tapetide-openapi.json (API source of truth). Goal: replace the Claude-run scheduled breakout scan with a Python job (GitHub Actions) that calls Tapetide REST (bearer token in TAPETIDE_TOKEN) and writes verdicts to the existing Supabase paper-trading tracker (strategy = 'breakout'). Claude is kept only for the "why" review of a small shortlist. Explore only: write no code and create no change yet.

Design constraint, treat as a hard requirement: ALL tunable parameters live in one config file (breakout.config.yaml): SMA/EMA periods, pivot lookback, volume multiples and baseline, stop %, position %, trim %, ATR bands, RS weights and thresholds, screen filters and post-filters, universe limits, exit-signal thresholds, schedule and quota. Strategy code is separate and contains no hardcoded numbers. Explore: config schema and validation (pydantic or JSON Schema), where each parameter is consumed, which parameters cannot be expressed in the Tapetide screener grammar (field:op:value, no multipliers) and so must be applied in code, how config changes are versioned and recorded per run in Supabase so results stay reproducible, and how a GitHub Actions run picks up an edited config.

Find in the OpenAPI spec, for each need, the exact route, params, response fields, limits and quota cost, and mark it COVERED / PARTIAL / GAP:
1. Weekly and daily bars: /v1/stocks/{symbol}/price (interval=weekly|daily, days up to 2000, end_date paging, adjusted OHLC vs raw_close, volume). Can one call return 450 weekly bars? How are the current partial week and holiday-short weeks represented? Can sessions per week be counted?
2. Screens: /v1/screens/technical and /v1/screens/fundamental. Can Q1 (down from 52w high < 4, price > DMA50 > DMA200, 1-week vs 1-year volume, mcap > 1000, avg vol > 100k, D/E < 3, pledge < 10) and Q2 (down from 52w high between 1.5 and 5, 1-week vol < 1-year vol) be expressed? Field names, operators, 100-row cap, no paging, and whether ROCE, quarterly profit/sales growth can be returned as extra columns for fundamental grading.
3. Relative strength: RS percentile from 3/6/9/12-month returns (/v1/market/heatmap/{index_slug} or screener perf fields), benchmark NIFTY 500 returns (/v1/indices/{slug}/levels).
4. Fundamentals and why-inputs: /v1/stocks/{symbol}/fundamentals (EPS and revenue YoY by quarter for acceleration, other income, CFO), promoter-pledge, shareholding, earnings-call digests, news and filings if present.
5. Risk checks: /v1/market/surveillance (ASM/GSM), circuit band or trade-for-trade status, turnover for stop-executability.
6. Live: /v1/quotes/live and /v1/quotes symbol limits, /v1/market/status (free) for trading-day gating, /v1/market/holidays, and when the Friday weekly bar is final.
7. Quota: /v1/me/usage, rate limits, error charging. Produce a per-run call budget for the Friday full scan (Q1 + Q2 + up to 8 deep-verify names) on Free vs Starter, and say whether the free 50/day is enough.

Also explore: which skill stages (1 Buy, 2 Trim, 3 Add, 4 Exit) need open-position state and an entry price, where that state lives (Supabase), and how the runner avoids assuming an entry price. Confirm how verdict tags map to the tracker and its process_ledger function.

Output: coverage matrix (requirement -> route -> fields -> status); GAP list with proposed owner (own code / Claude / manual); the proposed config file structure; open questions for me; and a recommended split into OpenSpec changes (for example: config-schema, tapetide-client, weekly-indicators, screen-intake, verdict-engine, supabase-writer, scheduler-and-alerts).
